# Design notes

Design decisions with their evidence. Most follow the installed EmDash source (`node_modules/emdash/src`, version 1.4.0); host paths are relative to that directory.

## EmDash APIs

| Topic | Decision and evidence |
|---|---|
| `getDb()` | `getDb()` is exported from `emdash/runtime`, not from the package root (`runtime.ts:17`, `loader.ts:1676`). `fromKysely(db)` takes the Kysely instance; the caller imports `getDb` from `emdash/runtime`. |
| Dialect detection | Core uses `instanceof PostgresAdapter` (`database/dialect-helpers.ts:33`). The plugin must not import `kysely` at runtime (the host owns that copy), so `detectDialect` checks the adapter class name and falls back to `supportsTransactionalDdl` (true only for the Postgres adapter among supported ones). `fromKysely(db, dialect)` accepts an explicit override. |
| Raw statements | The adapter passes a structural compiled query (`sql`, `parameters`, `RawNode`, `queryId`) to `Kysely.executeQuery`, the same shape `CompiledQuery.raw` builds. `?` placeholders become `$n` on Postgres. |
| `batch` | Sequential statements. D1 through Kysely has no transactions (`database/transaction.ts`), so batches are not atomic on any dialect. |
| KV | `KvLike` in `src/core/crypto.ts` is a structural subset of `KVAccess` (`plugins/types.ts:335`). `list(prefix)` returns keys without the plugin prefix (`plugins/context.ts:181`). |
| Settings field types | Field shapes follow `SettingField` (`plugins/types.ts:2012-2074`, exported from the package root). `secret` fields have no `default`. |
| Database self-check | No host route exposes the adapter `selfCheck`, so `privacy/receipt` runs it first and answers `503 db_unavailable` with the failure text, which the Data page shows as its banner. On success the receipt also carries `db.dialect` and `retention.storage`, so the page needs one route. A failed check does not stop writes. |

## Sessions

- A visit is one row of `ca_sessions` (primary key site, day, sid), with its page views and events as entries of one JSONB document (`hits`). `day` is the visit start day in the site time zone.
- Closed sid reuse: when the client sends a sid whose own row exists but is no longer active (window passed or `maxSessionMinutes` reached), the new visit cannot reuse that sid as its primary key. A random sid is created and the old sid is aliased to it, so the next page carrying the old sid joins the new visit. An alias lives one day (`MAX_VISIT_MINUTES`, the longest visit) and is written again only when its visit changes or less than half its life is left; whether the visit is still active is decided by the session rules, not by the alias. A sid whose alias points at an ended visit starts a new visit under a fresh sid, and the alias moves to it.
- `findActiveByVkey` returns the most recently seen candidate whose own window is open; `resolveSession` then applies the full `active()` check including `maxSessionMinutes`.
- The previous-day key is looked up only while `now < saltBoundary + W`, with `W` from the current setting. A visit that is still active later than that and is resolved without a sid starts again under the new key.
- Day rule: a page view or event counts on the day its visit started, also after midnight; orders, server events and error pages count on their own day. Hour charts of traffic use the hour the visit started; hour charts of orders use the order's own time.

## Settings

- If `scriptPath` equals `collectPath` after validation, both fall back to the defaults.
- List settings (`excludePaths`, `excludeIpPrefixes`, `ignoreReferrerHosts`, `queryAllowlist`, `downloadExtensions`, `ignorePathPrefixes`) are stored as strings and normalized to validated arrays; invalid entries are dropped.
- `ignorePathPrefixes` is a list of path prefixes, one per line or comma separated, default empty. Each item must start with `/`, be at most 256 characters and contain no word of `FORBIDDEN_PUBLIC_WORDS` (it is served in the page script config). For an anchor under a listed prefix the page script sends no `_download`; for a form submit whose same-host target is under it (the submitter's `formaction` first, then the form `action`) it sends no `_form`. Config key `i` in `clientConfig`. Reason: a form button that posts to a short link redirect would log a `_form` next to the redirect's own event. Link rules are not applied under a listed prefix either.
- `linkRules` is stored as a string of lines `<pattern> <event> [label]` and normalized by `parseLinkRules` (`src/link-rules.ts`) to an array of valid rules; a bad line is dropped by `normalizeSettings` and refused with its line number on save. Limits: 20 rules, 2,048 characters, pattern at most 200 characters (a `~` regular expression must pass `validateSafeRegex`), event `-` or `^[A-Za-z0-9.:-][A-Za-z0-9_.:-]{0,63}$` other than `seen` and `conv`, label 1 to 64 characters without whitespace, no word of `FORBIDDEN_PUBLIC_WORDS` on the line, no literal path prefix under an `ignorePathPrefixes` entry, no pattern twice. Config key `r` in `clientConfig`. The page script matches at click time against a target of at most 512 characters, compiling each regular expression inside `try`; the first match sends one event with the property `slug` and suppresses `_outbound` and `_download` for that click. `matchLinkRule` mirrors that match for the admin "Test a link" field.

## Channels

- Host-list conditions match the referrer host or `utm_source`. A `utm_source` without a dot is compared with the bare label of two-label list entries (`google.*` gives `google`), so `utm_source=google` is a search source while subdomain entries never match a bare word.
- Click ids: `gclid`, `msclkid`, `gbraid`, `wbraid`, `yclid` mean Paid Search; `ttclid`, `twclid` mean Paid Social; `fbclid` alone means Organic Social (the network adds it to organic links too).
- `newsletter` is accepted as an Email source and medium.
- Stored `source` is the referrer host, else `utm_source`, else `(not set)` when other UTM fields exist, else `(direct)`.

## Bot classification

- Order: empty or very short user agents first (always robots, no user rule can override them), then user rules that are not regexes, then the WebView allowlist, then built-in rules (curated, ai.robots.txt, crawler-user-agents), then user regex rules (at most 50, after the built-ins), then the generic fallbacks. A user `human` rule therefore overrides built-ins only in plain modes (`contains`, `prefix`, `exact`).
- crawler-user-agents entries take their category from the first upstream tag. Entries whose own sample user agents are already matched by an earlier rule are skipped to keep the table small. Any generated rule that matches a reference set of current browser user agents is dropped.
- The generic fallback is `bot|crawl(er|ing)|spider|scraper|fetch(er)|monitor(ing)|check(er)|probe` not followed by a letter, excluding the `cubot` phone brand; very short (under 10 characters) and empty user agents are robots.
- `src/query/safe-regex.ts` is a small parser for the RE2-like subset. A quantified group must not contain a quantifier or an alternation at all, which is stricter than "nested quantifiers" and also rejects patterns such as `(a?b)+`. Needed against polynomial backtracking (measured: `.*x.*!` takes about 200 ms on 512 characters): at most one open-ended repeat (`*`, `+`, `{m,}`) per pattern, two when it starts with `^` and has no top-level alternation, and at most 1000 combinations across `?` and `{m,n}` repeats.
- No crawler reporting: no crawler log exists. A robot never writes a row (`shouldRecordServerHit` is human, status >= 400 and `logErrorPages`); bots are counted only under the drop reason `bot`. There are no crawler settings, crawler report, crawler filter scope or tab; `tests/no-crawler.test.ts` guards it. The classifier keeps its `audience` field (bot exclusion, `skip_known_bots`), so the guard bans the SQL form `audience =` and not the `audience ===` comparison.

## Other

- `jsonExtract` inlines the validated key on both dialects instead of binding it on Postgres; the key must match `^[A-Za-z0-9_]{1,32}$`.
- `src/core/ids.ts` exports `validateIngest`, the pure validator of the ingest body that the `in` route uses; `src/contract.ts` holds the types. Out-of-range `nt`, `e` or `x` drop the field and keep the hit.

## Capture

| Topic | Decision and evidence |
|---|---|
| Raw 204 from routes | Routes declare `response: "raw"` and return `pluginResponse({ status: 204 })` (`plugins/route-wire.ts:205-303`, `plugin-types` `PLUGIN_ROUTE_RESPONSE_MODES`). Raw responses may only carry a fixed header allowlist (`route-wire.ts:16-26`, no `cache-control`); the host itself sets `Cache-Control: private, no-store` on every non-GET plugin response (`plugins/http-route-dispatch.ts:150-160`). The alias path sets `cache-control: no-store` itself. |
| Ingest answers | Page views and events are written before the response: 204 when stored or dropped by a rule (a malformed body included), 503 with `Retry-After: 5` on a failed write. Engagement updates go after the response (always 204). Only a body over 8,192 bytes is refused by the host. |
| `session` and `contract` bodies | Raw JSON responses with exactly the contract shape, not the host `{ success, data }` envelope. `contract` uses the route `cacheControl: "public, max-age=60"`, which the host applies to public GET responses. |
| Script tag markup | The host renderer writes `src` before `defer`: `<script src="/_/e.js" defer></script>` (`page/fragments.ts:61-68`). Same element, attribute order is the host's. |
| Degraded mode without middleware | A raw plugin route may not serve JavaScript (`route-wire.ts:27-40` rejects script media types), so there is no direct script URL. When this isolate's middleware has not handled a request and `mw:seen` is missing or older than 24 h, the hook emits the same code as one inline script pointed at `/_emdash/api/plugins/cookieless-analytics/in`. |
| Middleware liveness | The middleware also sets a per-isolate `globalThis` timestamp on every request; `page:fragments` checks it first, so a working install never renders the fallback while the KV marker is still being written after the response. |
| `mw:seen` from the middleware | Middleware has no plugin context, so `src/db/options-kv.ts` writes the same host `options` row the plugin KV uses (`plugin:<id>:<key>`, JSON value, `plugins/context.ts:150-180`, `database/repositories/options.ts:54-75`). |
| Middleware fail-open guard | `handleRequest` wraps the whole handler: a throwing settings read, `after`, `markSeen` or dispatch returns the `next()` response and logs one warning; `next()` runs at most once, and a rejecting `next()` rejects once with the site's own error. |
| Client IP | Routes use only the host `requestMeta.ip`. The middleware (no host meta) trusts `CF-Connecting-IP` only when `request.cf` exists, the host rule (`plugins/request-meta.ts:105-144`); `X-Forwarded-For` is never trusted. |
| Origin on the alias path | The host checks `Origin` only on `/_emdash/api/plugins/*`; the in-process dispatch skips it. The middleware applies the same rule to `collectPath`: a present `Origin` that differs from the site origin gets 204 without dispatch. |
| Plugin public paths | Methods other than `GET|HEAD` on `scriptPath` and `POST` on `collectPath` pass to the site and are never logged as server hits. |
| `scriptForBots = skip_known_bots` | `page:fragments` receives only page data, no request (`plugins/types.ts:1731-1733`). With the opt-in on, the middleware runs `next()` inside an `AsyncLocalStorage` holding the UA audience (`src/core/request-scope.ts`, a `globalThis` singleton shared by both bundles, the pattern of `request-context.ts`); the hook reads it. Default `always` never reads it. |
| Editor drop | `locals.user` is set by the host auth middleware (`astro/middleware/auth.ts:450-505`) and may be absent on site routes; the check is best effort. |
| Served word list | The script also reads `navigator.doNotTrack` (`signals = dnt_and_gpc`), a browser API name that contains `track`. The neutral footprint test exempts exactly `.sendBeacon` and `.doNotTrack`. |
| Reload dedupe | A reload starts a new page with a new sid, so the script cannot tell. The server drops a page view that continues a visit on the same path within `reloadDedupeSeconds` (drop reason `reload`). `maxPageviewsPerSession` (500) and `maxEventsPerSession` (200) are enforced in the same place (drop reason `session_cap`). |
| Hidden documents | A page that loads hidden (background tab, prerender) sends nothing until it becomes visible, then starts normally. |
| Hit ids | Page views are entries of the visit document keyed by the client hit id `h`; events by `e` plus their client event id (a random id when the sender gives none), so they never collide with their page's page view and a retried event is stored once. The client sid the page sent finds the visit directly or through its alias row, so engagement updates match without resolution. A replayed page view or event writes no row. |
| Engagement updates | One statement on the visit row raises only the fields present in the update on the page view's entry (`d`, `e`, `s`, `x`), and the visit totals move by the difference to the stored value, so a repeated or reordered update adds nothing and an update without `x` leaves the exit kind unset. An update for a page view not stored yet may open the entry while the document is below 64 KB (`MAX_DOC_BYTES`). |
| Write coalescing | None: a page view or event on a known visit is one statement and one row written on its visit row, so there is nothing to coalesce. |
| Human error page referrer | Error pages are counters in `ca_srv` per day, status, path and `ref` (the external referrer host and path, `''` when none), with the time of the last one. |
| Host column | `RequestInfo.host` is `URL.hostname` (lowercase, no port). A visit takes it from the entry request; a page view on another linked host stores its own host in the entry field `hs`. |
| Annotations path | Content hooks carry no URL (`plugins/types.ts:1456-1459`, `emdash-runtime.ts:582`); the path comes from the host as described under Annotation scopes. Saves of already published items (`content:afterSave`, not new, status `published`) become `update` annotations, one per item and day, when `annotateUpdate` is on (off by default). `autoAnnotations`, `annotatePublish`, `annotateCollections` and `autoAnnotationsPerDay` are checked before any read of the path; the day's ids sit in one plugin KV entry (`annotations:auto`), one read and at most one write per hook, no database query. |
| User agent rules in the middleware | The middleware has no plugin storage access, so its classification (`skip_known_bots`, `locals.<ns>`, the error page decision) uses built-in rules only. The `in` and `session` routes apply user rules. |
| Caps and drop counters | Per-sid, per-vkey and session read caps are per-isolate minute counters (LRU of 5000), so limits are approximate across isolates. Drop counters are kept per isolate and flushed to `ca_drops` (one row per site, day and reason) once the oldest count is 10 s old and after cron jobs; an isolate that ends loses up to 10 s of counts, so the counters are a lower bound. |
| History rule | The page script makes no history call at all. `src/client/boot.ts` has no history reference, no fragment handling and writes no address. History methods are not wrapped and there is no `popstate` listener; route changes come from `astro:page-load` and `window.<ns>.page()` only. A `pushState` by the page alone sends no page view (tested). A full page load joins its visit through the visitor key. |
| History guard | Scans every `.ts` file in `src/client`, including `generated.ts`, and fails on any reference to `history`, `replaceState`, `pushState`, `popstate`, `location.replace`, `location.assign` or a `.hash` access. `tests/client.test.ts` and `tests/gate/hostile.test.ts` pin at run time that no history method is called and that any fragment is left in the address. |
| Engagement timing | One update per hidden period (the latch reopens when the page becomes visible) and always one on `pagehide`, even right after a hidden update, so the exit kind 1 or 2 is never lost to the latch. The update before a route change carries no `x`: it is not an exit. Visible time is counted from the script's own visibility state, so the last segment before `visibilitychange` to hidden counts (the active time gains the same fix). |
| Search re-entry | Needs `n = 1`, a search referrer, `continue`, and `nt` 0 or absent: a reload or a back or forward load keeps the original search referrer and would otherwise count as a re-entry. |
| Script key | Read once at the very start of `boot()`, before the bail-outs, because `currentScript` is only set during the first synchronous run. An inline script (no `src`) never reads a key, so a `?k=` in the page address cannot redirect or drop the master's own events. A key that is not 20 lowercase letters and digits is ignored. |
| Page script size | 4,835 bytes minified, 2,466 bytes gzipped; a test keeps the gzipped size under 3,072 bytes ([performance.md](performance.md)). |

## Query engine

| Topic | Decision and evidence |
|---|---|
| `IN` chunks | Each chunk of up to 90 values binds one JSON array: `col IN (SELECT value FROM json_each(?))` on SQLite and D1, `col IN (SELECT jsonb_array_elements_text(CAST(? AS jsonb)))` on Postgres. One-parameter-per-value chunks cannot be combined in one statement under the D1 limit of 100 (three chunks of 90 already exceed it), and a regex expansion of up to 5000 matches must still fit. 250 values give 3 chunks and 3 parameters. Filters together may use at most 60 parameters (`too_many_values` otherwise). |
| Parameter limit | Report statements are checked before they run (`too_many_values` above 100 on every dialect); tests run every statement through the same check. |
| Hit dims | Session dims are predicates on `ca_sessions s`; hit dims are `EXISTS` over the entries of the visit's own document (`json_each(s.hits)`, Postgres `jsonb_each`); hit-level reports also restrict their own entry rows. |
| Negated operators | Session columns: `col IS NULL OR NOT (...)`, so rows without a value count as "not X". Hit dims: `NOT EXISTS` over the document entries. |
| `contains` and `prefix` | `lower(col) LIKE lower(?) ESCAPE '\'`; integer columns (`status`) compare `CAST(col AS TEXT)`. |
| Event property values | Wrapped in `CAST(... AS TEXT)` on SQLite so numeric properties compare with the strings users type. JSON booleans read as `1` and `0` on SQLite and `true` and `false` on Postgres. |
| Regex sources | Session dims read `ca_sessions` in range, hit dims the document entries of the dim's kind, search dims `ca_search_daily`. A `page` regex is expanded over page view entries and error page paths together, because `page` also restricts Not found. Over 5000 distinct values, or a pattern matching more than the match limit, answers `narrow_filter`. |
| Hit-level rows | `page` filters restrict page view entries (Pages, Not found), `event` and `event_prop` filters restrict event entries. `goal` filters restrict visits only. Funnels and Goals apply visit-level filters only, so a page filter cannot remove other steps. |
| Goal match types | `contains` is accepted for every goal type. Outbound `is` matches `p.url` equal to the host or starting with `host/`. |
| Day attribution | See the day rule under Sessions: page views and events count on their visit's start day, orders, server events and error pages on their own day. |
| Page views in Overview | Sum of `ca_sessions.pageviews` over the filtered visits, consistent with "a filter restricts the set of visits". |
| Exit rate | Exits are filtered visits in range whose `exit_path` is the page. |
| Scroll median | Lower median of the stored per-page-view maximum scroll, computed from a value histogram. |
| Landing exit | A correlated `MAX` of the exit field over the page view entries of the visit's own document, evaluated only for single-page visits. Same result, and no join that could double a visit's counts. |
| Search join on Pages | One grouped read of page grain rows (`query = country = device = ''`) for the paths of the current result page, merged in code; rows without search data get nulls. Equivalent result, one statement, no join fan-out. The page key compared with a page view's path is the path (no origin): Search sources store `page_key` as the normalized path of URLs on the site's own origin. |
| Search sync writes | A pull counts the stored rows per day in one read, then compares the pulled rows of the days that have stored rows with them (EXCEPT in both directions over every column, in groups under 400,000 characters of JSON); a day with nothing stored needs no comparison and replaces only the days that differ, so a window equal to what is stored writes no row. A day over the group size is not compared and is replaced. The write stays a delete plus inserts per day: the primary key is the natural key, but vanished rows must go and the cost of a write must be known before it runs for the rows budget. |
| Search grains | Each search report reads the smallest stored grain holding its group dim and every filter dim: totals, page, query, country, device, or page with query. Other combinations (for example page and country) return `unsupported_filter`. Traffic dims in search reports are ignored with the notice `ignored_dim:<dim>`. |
| Not found and filters | Only `page` filters apply (error page counters have no visit); others add the notice `filters_not_applied`. |
| Report parameters | Report-specific inputs travel in one `params` object (`withSearch`, `field`, `event`, `funnel`, `steps`, `source`, `page`, `dim`, `prop`, `prefix`, `scope`), validated by zod. |
| Compare output | Totals gain `compareTotals` and `delta`; rows gain `previous` and `delta` (relative change, null when the previous value is 0 or missing), matched by key; series gain `compareSeries` aligned by index. |
| Typed errors | Thrown as host `PluginRouteError` with status 400 and codes such as `narrow_filter` (regex expansion too large), `narrow_range` (detailed report over the scan budget), `raw_only` (report needs detailed rows before the detailed window), `invalid_regex`, `unknown_goal`, `unknown_funnel`, `unknown_segment`, `funnel_cap`, `journey_range`, `journey_cap`, `too_many_values`, `unsupported_filter`, `invalid_params`, `invalid_filter`, `invalid_currency`, `compare_not_supported` (`QueryErrorCode` in `src/query/compile.ts`; host `plugins/route-error.ts`, `plugins/routes.ts:296`). |
| Range cap | 1000 days on the admin route. |
| Funnel order | `ts` has whole seconds, so hits sharing a second may satisfy consecutive steps in either order. |
| Goal conversions | Converting visits are counted among the same visits as the denominator (started in range, with a page view, matching the filters). |
| `zod` | `zod` is a runtime dependency of the package and external in the build (the host already ships the same major), so the route `input` schema is a real zod schema the host validates with `safeParse` (`plugins/routes.ts:245`). |

## Summaries, retention, routes and cron

| Topic | Decision and evidence |
|---|---|
| `ca_rollup` columns | Column meaning depends on the dim. Visit dims: `engaged_ms` holds the summed visit duration in ms (`max(last_seen - started, visible_ms)`, the value avg duration needs), `hits` is 0 except on the `all` row, where it holds the day's passive entries (link impressions) for the storage estimate. `page`: `sessions` are distinct visits with a view, `engaged_ms` the summed active time, `hits` the views with a measured active time (the avg active time denominator). `event`: `events` count, `sessions`, `visitors`. `goal`: `events` completions, `sessions` converting visits. Documented in `src/query/rollup.ts`. |
| Summary dims and keys | Single dimension families: all, page, entry, exit, channel, source, utm_campaign, country, device, browser, os, lang, event, goal, revenue. Keys use the same expressions as the detailed breakdowns (`(not set)` for missing values; `utm_campaign` only where set), and every family counts by the visit start day, so a stored day equals the detailed query for that day (test). Top N per dim and day: `page`, `entry`, `exit` 500; every other dim 200; the rest folds into `(other)` with summed visitors. Internal `_` events are not summarized (their reports are detailed only). |
| Summary cadence | A day is stored once, when it closes: at the first tick 15 minutes after the local midnight that starts day D + 2 (`lastClosedDay`, `CLOSE_GRACE_S`). Today and yesterday (until closed) are never stored; readers compute them from the visits on read with the same function that stores them (cached 60 s per isolate), at most the newest 4 such days (`MAX_OPEN_DAYS`). Rows are written with a changed-rows upsert, so storing an unchanged day again writes 0 rows and an idle tick runs no statement. A tick walks the closed days after `rollup:watermark` (first run: from the oldest visit or order day), oldest first, site by site, until the request budget of `capacityProfile` is spent, and keeps its position in `rollup:cursor`. The watermark moves only when every site holds the day. |
| Compound SELECT limit | D1 allows at most 5 terms in one compound SELECT, so the plugin runs a union of more parts as the fewest statements of at most 5 terms and at most 100 bound parameters, in order, and concatenates their rows (`unionAllChunked`, `src/db/compound.ts`); a fixed union of up to 5 parts goes through `unionAll`, which refuses more, and no other source file joins SELECTs (`tests/issue-22-d1-compound.test.ts`). A closed day costs 26 statements without goals: the visit read 5 (21 parts), pages, events, revenue 2 (9 parts), links 3 (15 parts), journeys and 13 writes, plus one per five active goals and one per five event goals. The test databases refuse more than 5 terms with D1's own error, and also LIKE patterns over 50 bytes, statements over 100 KB and results over 100 columns (`tests/d1-limits.ts`). |
| Summary pairs | Besides the single dimension rows (`seg = ''`), `ca_rollup` stores pair rows for page, entry page, source, campaign, event, goal and link, each crossed with channel, country and device (`seg` names the segment, `segkey` its value), and `ca_revenue_daily` the same pairs per currency. They are computed in the same reads as the single dimension rows (the visit read joins the 11 dimensions, the 9 visit pairs and the cube cells as 21 parts). Rows per site and day across all pairs: 340 (`small`), 7,500 (`standard`), 15,000 (`dedicated`), split by fixed weights (`PAIR_WEIGHTS`: page 4, entry page, source and event 2, campaign, goal and link 1, for each segment); within a family the top rows by visits (revenue: by orders) are kept, and the rest fold into key `(other)` of their segment value, or `(other)` x `(other)` for a segment value with no kept row, so every total stays exact. Readers of single dimension rows filter `seg = ''`. |
| Summary cube | `ca_cube` holds one row per site, day, channel, country and device (visits, page views, visitors, bounces, engaged, duration, events), computed in the same visit read as the single dimension rows. Orders per cell go to `ca_revenue_daily` as dim `all`, seg `cube` (segkey: the three values), per currency. Cells per site and day: 150 (`small`), 1,000 (`standard`, `dedicated`); beyond them the smallest countries fold into country `(other)` of their channel and device (a channel and device with no kept cell into `(other)` x3), so totals and every kept channel and device stay exact. |
| Link and journey summaries | Links: the top 200 links and 200 placements per day (`LINK_TOP_N`), plus link pairs within their share of the pair budget. Journeys: `next` rows (a page and its next page, `(exit)`, the entry pages under `(entry)`, and the visits of each page) and `path3` rows (the entry page and the next two steps), one statement per day; each day keeps up to 2,000 step rows (the steps within a third of that, plus the pages they name) and 500 three-step paths (`small`: 200 and 50), the rest folds into `(other)` per page. A visit counts on its start day, so the rows of several days add up exactly; a sid that starts visits on two days counts twice where the detailed report counts it once. |
| Visitors in summary data | Summed over days and over cube cells: a visitor of two channels on one day counts once per channel when channel is not filtered. |
| Detailed window and routing | The detailed window starts `rawDays` days before today (site time); `rawDays` is `rawRetentionDays` (default 760, 7 to 760), or the shorter value the storage budget of `capacityProfile` allows (stored in `retention:cursor`). A traffic report whose range starts before it reads the summaries: the stored days plus the open days computed on read, so today in such a range is current. Inside the window the summaries also answer when the stored `all` rows of the range hold more visits than the scan budget (`SCAN_BUDGET`: small 50,000, standard and dedicated 500,000) and the summaries apply every filter; otherwise the detailed report runs up to 4 times the budget and beyond that is refused with `narrow_range`, naming the longest range that fits. Compare ranges decide on their own; `compare_summary` notes it. The cursor also keeps the visit cutoff last applied, and the window never starts before it, so raising `rawRetentionDays` reads the summaries for days whose visits are already gone. `tools/rollup-now` refuses days before the window (`raw_gone`), so a stored day is never rebuilt from deleted rows. |
| Filters in summary data | A breakdown applies filters on its own dim; Overview and Timeseries apply filters of one visit dim. One of channel, country and device combines with page, entry, source, utm_campaign, event, goal or link through a pair row. Two or three of them combine with each other through the cube for Overview, Timeseries, the channel, country and device breakdowns and revenue totals, series and breakdowns by channel, country or device; beside a page-like breakdown or a filter on another visit dim a second one stays `combination`. ## API keys and agent API

| Topic | Decision and evidence |
|---|---|
| Route names with slashes | The catch-all passes the rest path (`astro/routes/api/plugins/[pluginId]/[...path].ts`) and `getPluginRouteMeta` indexes `routes` with the path minus its leading slash (`emdash-runtime.ts:5565`); `routeNameSchema` allows `/` (`@emdash-cms/plugin-types`). So `agent/v1/query` and the other names resolve as is: no flat names, no alias. The real dispatcher cannot be loaded under vitest (it pulls media dependencies such as `image-size`), so `tests/agent-routes.test.ts` runs the same lookup and cache rule over the routes of `createPlugin()`. |
| Auth before validation | The agent routes declare no `input` schema and no `permission`: the host validates a declared schema before the handler and would answer 400 to a caller without a key. The handler checks the key, the rate limit and the scope, then parses. Input comes from the host default parsing (JSON body for POST, query string for GET); a POST body that is not JSON gets the host 400 before the handler, which tells nothing about keys. |
| Raw responses | `response: "raw"`, so the plugin sets the status (404 `{}`, 400, 429 with `Retry-After`) and the body is the envelope itself, not wrapped by the host `apiSuccess`. |
| Missing scope | 404 `{}`, identical to a bad key, so a key cannot probe what other scopes unlock. `query` returns that 404 before parsing when the key has neither read scope, so such a key sees no validation errors. |
| Errors | Invalid input is 400 `{ ok: false, error, message }` with `invalid_input`, `site_not_allowed`, `unknown_site`, `range_too_long`, or the query engine code (`invalid_regex`, `narrow_filter`, `narrow_range`, `raw_only`, `too_many_values`, `unknown_segment` and the others listed under Typed errors). The rate limit is 429 `rate_limited` and is applied after auth (traffic without a key is left to the WAF). |
| `query` body | `{ report, query, limit?, offset?, params? }`: `params` (funnels, event properties, dimension values, the per-page search queries and `withSearch` need it). Scopes are decided per report after parsing: `search_*` and `dimension_values` with `params.scope: "search"` need `read:search`; `pages` with `withSearch` needs both read scopes. |
| `openapi.json` | Needs any valid key (no scope), like every agent route. The catalog and OpenAPI document are not tied to a site, so a site-restricted key reads them. |
| Search routes | Registered with their scope and body schemas; without a Search source that can sync on the site both answer 400 `search_unavailable`. `status.search` reads the `search:state:<site>:<source>` KV entries of the answered site and passes only the scalar fields `lastRun`, `status` and `lastError` (`SEARCH_STATE_FIELDS`). |
| Dates | Range parameters of `summary` and `annotations` must be real calendar days (`2026-02-30` and `0000-00-00` are `invalid_input`), so the 400 day range cap cannot be skipped through `NaN`. |
| Defaults | `summary` defaults to the last 7 days with today, `annotations` GET to the last 30 days (at most 500 items, newest first). Posted annotations take `kind` `release` (default) or `manual`. Freshness in `status` is `lastHumanDay`, the newest visit day (`MAX(day)` of `ca_sessions`, a visit start day). |
| Key store | Item ids are random; `verifyKey` queries the `prefix` index, hashes the secret and compares in constant time. `last_used` is throttled from the stored value, so every request costs one storage query and at most one write per 10 minutes. The `last_used` write and revoke use the host `updateIf` with `set` (a field merge, `plugins/types.ts`), so a request that read the key before a revoke cannot write `revoked: false` back. At most 100 keys per install including revoked ones (revoked keys stay listed until `keys/delete` removes them; only a revoked key can be deleted). |
| Key sites | A key without a `sites` field reads as "every site". The admin offers the restriction only when client sites exist. The restriction is checked right after auth and the rate limit, before any parsing, and answers the same 404 `{}`. |
| Agent `site` | `query.site` for `query`, `?site=` for `summary`, `status` and `GET annotations`, a `site` body field for `POST annotations`, `search/sync` and `search/backfill`. A `query` call by a key without a read scope stays 404 whatever the site. |
| Admin expiry | The admin picks a day; the key is valid through that day in the site timezone. The route takes epoch seconds and rejects past values. |
| OpenAPI build | `scripts/build-openapi.mjs` (`pnpm openapi`, `--check` for CI) loads `src/agent/openapi.ts` with Node type stripping and a resolve hook that maps `./x.js` imports to `./x.ts` (`module.registerHooks`, Node 22.15 or later), plus a load hook that adds the JSON import attribute (`settings.ts` imports `src/data/currencies.json`). For that, `QueryError` declares `code` as a plain field instead of a constructor parameter property, which strip-only mode rejects. The served document is built at runtime from the same function and the plugin `VERSION`. |

## Revenue and server events

| Topic | Decision and evidence |
|---|---|
| Storage | Orders and server-reported events are one row each in `ca_events` (site, id), with the visit (`sday`, `sid`) when known, amount `val` and currency `cur`. Browser and agent orders share the table, so one order is one row whatever its origin. An event attached to a visit is also an entry of that visit's document, so hit-level reports see it like a browser event. |
| Agent event statements | Set based: three reads (order ids, visits, aliases joined to their canonical visit), one insert per 9 events and one document update per attached visit, so a call of 20 events costs at most 26 statements (6 plus one per distinct visit). A `sid` attaches to a visit at most 7 days old (`AGENT_ATTACH_DAYS`). |
| Agent last word | Agent inserts end in `DO UPDATE`: a repost replaces `val` and `cur` and keeps time, day, path and name; the browser and in-process path never change an existing order (counted as `duplicate_order` in `ca_drops`). The agent route reports repeats in `data.duplicates` instead, since the caller sees them. |
| Order retried before its visit existed | The browser order row is written first, then the visit. When an attempt stores the row while the client sid has no visit yet (the order is the first event of a fresh sid) and then fails before the visit write, the row is kept with no visit (`sday`, `sid` null). Every retry conflicts on that row and is counted as `duplicate_order`, so the order keeps its row and amount (revenue reports count it) but no visit and no entry: it is missing from hit-level reports and from revenue by source and page. A retry cannot tell such a row from an agent's unattributed order, which a browser post must never claim (see "Agent last word"), and taking the row over would cost a row on that duplicate; so it is not repaired. An order row attached to a visit whose entry is missing is repaired on the retry. Measured in the loss test with overloads and killed isolates: 0 to 2 of 135 orders. |
| Agent event ids and host | Orders `o.<hash>` of site, name and order id (`orderHitId`); other events `a.<20 random characters>`. `host` is null: a server call has no page host. |
| Agent event reasons | Adds `invalid_path` for a `u` that is not a same-origin path (storing the event without its path would silently attribute it to another page) `unknown_order` for a void or refund of an order that is not stored, and for refunds `refund_exceeds_order` (refunded total above the order's amount, or a voided order) and `currency_mismatch` (a `cur` other than the order's). An item that is not an object is `invalid_name`. |
| Refunds | A refund item `{ name, oid, rid, refund }` on `agent/v1/events` stores one `ca_events` row with the order's visit, page, name and currency, `val` the negative amount, on the refund's own day; its id is `<order row id>.r<hash of rid>`, inside the key range of the order, so retries are stored once and the refunded total is one key range read. Reports count orders, gross revenue and paying sessions on `val >= 0` and add `refunds` and `net_revenue`; `ca_revenue_daily` holds refunds as rows of dim `refund.<dim>`. No schema or layout change. Link revenue and the `sites_summary` revenue stay gross. |
| Repeats inside one call | A repeated `oid` inside one call edits the pending row (last amount wins) and counts as a duplicate: one upsert statement must not touch a row twice (Postgres refuses). A void is valid only for an order the first select found, so a void of an order posted earlier in the same call is `unknown_order`. |
| Void item validation | `void` other than `true`, or with a `val`, is `invalid_value`; a missing or malformed `oid` is `invalid_id`; `ts`, `sid`, `u`, `p` and `cur` of a void are ignored, since the row keeps its own. |
| Sid gained on a repeat | `sid = COALESCE(ca_events.sid, excluded.sid)` and duplicates do not raise `events`: an unattributed order that a later agent post attaches to a visit does not raise that visit's `events`, so `events` can be one lower than the event rows of that visit. |
| `ts` clamp | 30 days back, and not before the first day of the detailed window (`rawFromDay`, read once per call). |
| Rounding | On write, in the recorder and in `recordAgentEvents`: the exponent depends on the effective currency, which is only known once the site default is resolved. `validateIngest` checks range and type only. |
| Currency list | 155 codes. Also left out: the fund and special codes (BOV, CHE, CHW, CLF, COU, MXV, USN, UYI, UYW, XDR, XSU, XUA and the bond units), because CLF and UYW have exponent 4, outside the supported 0, 2 or 3, and no shop prices in them; and the withdrawn ANG, BGN, CUC, HRK, SLL and ZWL. Their successors XCG, SLE, VED and ZWG are listed. |

## Multi-site master

| Topic | Decision and evidence |
|---|---|
| Options reach `createPlugin` | Confirmed: the generated module calls `createPlugin(JSON.stringify(descriptor.options ?? {}))` for native plugins (`astro/integration/virtual-modules.ts:302`). `cookielessAnalytics(options)` validates the options, puts them on the descriptor only when `sites` is not empty, and declares the derived `allowedHosts` on both the descriptor and `definePlugin`. |
| Remote id against `siteId` | `siteId` is a plugin setting read from the database, which `createPlugin` cannot read (it runs synchronously when the module loads). `createPlugin` refuses the default `siteId` (`default`), `all` and duplicates; at runtime this database wins: a remote id equal to the current `siteId` or to a client site id is not listed by `sites/list` and `data/query` answers it locally. |
| Forwarded body | The body is forwarded unchanged except `query.site`, which is left out so the satellite answers its own local site whatever its `siteId` is; with the master's id the satellite would answer `unknown_site`. | `data/export` | Proxied like `data/query` (same body, same errors), then exported on the master. |
| Error shape | The admin route throws the host `PluginRouteError` with code `remote_error`, HTTP status 502 and `details: { status, reason }`; `reason` is `key_missing`, `not_configured`, `no_http`, `timeout` (status 504), `too_large`, `network` (502), `invalid` (not the agent envelope) or `http` (the satellite's status, a redirect the host did not follow included). The satellite's body is never included. |
| Redirects | `ctx.http.fetch` is called with `redirect: "error"` (`plugins/http-wire.ts:146`), so neither the host nor the plugin follows a redirect: the host keeps custom headers on a followed redirect, which would send the satellite key to whatever allowed host the redirect names. A redirect is a `remote_error` (`network` when the host refuses it, `http` with the status if a 3xx reaches the plugin). Point `origin` at the satellite's canonical host. |
| Cache | Keyed by satellite id, method, path and the JSON body string (no hash needed in memory); successes only, at most 200 entries per isolate, so a fixed key or a recovered satellite works at once. |
| Timeout | `Promise.race` with a timer plus an `AbortSignal` passed to `ctx.http.fetch`, so a host that ignores the signal still cannot hold the route. |
| Remote summary rows | `agent/v1/summary` takes the optional `compare` (`previous` default, `year`, `none`) and returns `data.revenue` (`[{ currency, revenue, orders }]`) so one call gives the row and its delta for the header's comparison.
